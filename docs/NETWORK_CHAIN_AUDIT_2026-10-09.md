## 建议先修的缺陷

### 1. 公共 JSON 请求中断后可能一直不结束

位置：`server.js:1875–1903`，`requestText`。

只有请求对象 error 监听，没有响应对象 aborted/error 结算；只设置 socket 空闲超时，没有总请求截止时间。本机 HTTP 夹具发送不完整 Content-Length 后断开，200ms 后 Promise 仍未结算；另一个持续滴流夹具设置 timeoutMs=30，却在约210ms 后成功，证实该值不是总期限。

影响：用该封装的 QQ/其他元数据请求可能持续占用加载态；切走界面也不一定释放后台任务。修复建议：统一一次性 resolve/reject、响应中断监听、总 deadline、AbortSignal 和有界响应体。不要把暂时网络问题改报为账号过期。

### 2. 切歌过早关闭音频代理时，旧上游仍会下载

位置：`server.js:6835–6872`，`/api/audio`。

在等待上游 headers 后才监听 `res.close`；用户若在 headers 返回前离开，关闭事件已经错过，而且 fetch 未传 signal。真实 loopback ServerResponse 配合假上游复现：下游早关闭后仍读完整24MiB，上游 cancel次数为0。

修复建议：请求开始即登记关闭/AbortController；headers返回后再检查 destroyed；把 signal 传入上游。此项只处理已断开的客户端，不推翻项目原先保留的“正常暂停时继续拉取并溢出到临时文件”取舍。

### 3. 音质降级上限没有恢复机制

位置：`public/js/modules/05-playback/00-api-quality-output.js:175–211,309–323`。

runtime cap 只降不升，key 不含账号，记录的 at 未用于过期。普通账号或暂时失败把一首歌降级后，切换到有权限的会员账号或主动选择高音质，仍会被旧 cap 拦住，直到重启。隔离 VM 已复现。

修复建议：区分版权/权限限制与网络临时失败；上限关联授权会话并设合理过期；重新登录、权益更新及用户显式重试时允许重新探测一次，避免无限高音质重试。

### 4. 汽水缓存清除后，旧请求可覆盖新数据

位置：`qishui-api.js:138–170` 的 `createTtlCache`；歌单/收藏更新后的 `invalidateQishuiLibraryCaches` 与最近播放上报均调用 clear。

clear只清Map，没有改变请求代次。隔离复现：旧请求挂起→clear→新请求写入新歌单→旧请求返回，再次把旧歌单存进缓存。旧 finally 也可能删除新任务的 inflight 项。

修复建议：缓存代次校验，只有当前代次结果可写；清理 inflight 时核对 Promise 身份。缓存key已含账号指纹，本发现不等于跨账号泄漏。

### 5. 评论请求没有完整超时/取消流程

位置：`06-track-detail-lyrics-actions.js:515–523,565–568,654–655,760–761`；`06a-comment-replies.js:81–123`；`apiJson` 默认 timeout 为0。

评论/回复请求悬挂时 loading 持续为true；关闭、换歌曲或排序只丢弃旧结果，网络请求继续。现有 owner/seq 确实能防止旧内容串入新详情，应保留。

修复建议：每个评论owner管理读取任务AbortController，GET加deadline；关闭/重载取消旧GET，取消不显示为加载错误；不要把用户已提交的评论POST一起取消或自动重试。

### 6. 楼中楼整页重复时错误显示到底

位置：`06a-comment-replies.js:94–113`。

`hasMore` 同时要求 fresh.length>0。上游页出现重复内容但cursor继续前进时，去重后为0会隐藏加载更多。已复现 A→重复A(cursor2) 后无法请求下一页B。

修复建议：去重只控制DOM插入；是否继续由hasMore和前进的cursor/offset决定；可对连续空进展设置有限保护，不能一页重复即终止。

### 7. 评论头像恢复联网后仍可能一直占位

位置：`06b-comment-avatars.js:65,81–82,100–105`。

两次失败设置30秒冷却；online只重扫，会被冷却拦住；没有冷却到期自动重扫。VM中联网40秒后仍未重试，手动滚动/scan才恢复。

修复建议：online对当前可见失败项清冷却并有限重试，或到期重扫可见项；不重试隐藏或已经移除的头像。

## 其他播放边界

- 解密音频缓冲的后缀 Range：`sendAudioBuffer` 对 bytes=-3 应返回最后3字节，目前可返回前4字节。需覆盖后缀、开放端点、超范围与空缓冲；不是所有正常播放都会触发此Range形式。
- 临时文件短写：`audio-spill-relay.js:125–127` 忽略 FileHandle.write 返回的 bytesWritten；假文件句柄短写可导致音频缺字节。应循环补写并按实际字节推进偏移，处理0字节进展。真实磁盘短写频率未测。
- 已失效的专辑预加载任务：虽能防止旧结果真正播放，但部分搜索→换平台取链步骤缺少中途有效性检查，继续消耗请求。应先补代次检查与可取消网络任务，不能只在结尾丢弃结果。

## 封面可选优化（需测量收益）

位置：`cover-cache.js:8–15,42–50`；`server.js:895–926,6812`。

当前成功缓存有容量/TTL，单URL请求会合并，下载有16MiB单体上限和每块读取闲置超时。但不同URL的在途任务没有全局并发/字节预算，也没有整个下载的总期限；前端超时后，上游任务不一定被取消。

隔离机制验证：32个不同URL同时启动，pending=32而完成缓存bytes=0；虚拟每5秒滴一块、持续45秒仍成功。它不证明真实使用一定达到该峰值。

建议：封面专用总deadline、并发/在途字节预算、有界队列；共享任务按订阅者计数，最后一个订阅者退出才取消。保留已有同URL合并、可见优先、内容类型/大小检查和DNS安全约束，不扩大fake-IP域名范围。
